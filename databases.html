Connecting to a Database

Once an app needs to remember things for more than one person, it needs a real database. This guide uses a worked example — a family birthday calendar — to explain what the database is for, and then walks through every setting you have to configure, and why each one exists. The database is the easy part. The configuration around it is where the time goes, because a wrong setting usually fails silently or with a misleading error.

1
Why the App Needs a Database concept
01
Shared. Five people, five phones, one list of birthdays. Everyone has to see the same thing, and an edit made on one device has to show up on the others
02
Durable. It has to survive a cleared browser, a new phone, a lost laptop. Anything stored only in the browser is one wipe away from gone
03
Readable when nobody is there. A job runs at 7am to send birthday reminders. No one is signed in. No browser is open. Something still has to read the list
💡 That third one is the decisive requirement. Browser storage can just about fake the first two — it cannot do the third at all. If your app only ever shows data to the person who typed it in, you may not need a database yet. The moment something has to happen on a schedule, or be seen by someone else, you do.
2
Why Firebase, and What We Set Up ~5 min
01
Firebase is Google's app platform. It gives you two things in one place: Authentication (who are you?) and Firestore (the data itself)
02
There is no server to run or patch — the app talks to Firestore directly. It is free at family scale, and it syncs live, so an edit on one phone appears on the others with no refresh
03
We use one Firebase project called phil-mini-apps on the free Spark plan, shared by every mini app. The family signs in with the same email and password everywhere, and each app keeps its own collections inside that one project
💡 Sign-in method is email + password, restricted to an allowlist of family addresses. A stranger can reach the login page, but their account is not on the list, so the rules in step 4 refuse them.
3
The Two Kinds of Credential the crux
01
There are two different doors into the same database, and confusing them is the single most common mistake. The browser comes in one way; the 7am job comes in the other
02
The public one — the Firebase web config. Keys like VITE_FIREBASE_API_KEY ship inside the page and anyone can read them out of the source. That is fine and by design: they say which project to talk to. They authorise nothing
03
The private one — the service account key. A key that reads and writes anything and ignores every rule. It is how the 7am job gets in with nobody signed in, and it must never leave the server
⚠️ Security does not come from hiding the public config — it comes from the rules in step 4. But the service account key is a genuine secret. A VITE_ prefix means "put this in the browser bundle", so if a secret ever gets that prefix, you have published it. Treat that key like a password, and revoke it if it leaks.
4
Publish the Security Rules ~5 min
01
Go to console.firebase.google.com → your project → Firestore Database → Rules
02
The rules say who may read and write each collection. For the birthday app: the data collections are readable and writable only if your signed-in email is on the family list, and the two server-only collections are denied to everybody
03
Add your app's blocks inside the existing match /databases/{database}/documents { … } block, then click Publish. It takes effect in seconds
⚠️ Paste as a fragment — never replace the whole ruleset. One project shared by several apps has one ruleset. Paste over the top and you silently delete another app's rules. Firestore reports a missing rule as an ordinary "permission denied", so the app you just broke looks like it has a bug in it.
5
Create the Service Account Key ~5 min
01
In the Firebase console: Project settings → Service accounts → Generate new private key. A .json file downloads, and it is shown only once
02
Put it where the server can read it — for a Vercel app that is Settings → Environment Variables. Name it FIREBASE_SERVICE_ACCOUNT and paste the whole JSON as the value
03
Redeploy. Environment variables are read when the app builds and runs, so an existing deployment will not pick up a new one on its own
💡 How it is actually used: the job signs a short-lived token with that private key, swaps it with Google for an access token, and calls the database directly. No password, no user, no rules. Until you set it, the job says so plainly — "FIREBASE_SERVICE_ACCOUNT is not set."
6
Authorised Domain + API Key Referrer ~5 min
01
A — Firebase. Authentication → Settings → Authorised domains → add your app's domain. Firebase only accepts a sign-in from a domain you have listed
02
B — Google Cloud. console.cloud.google.com/apis/credentials → your browser API key → Website restrictions → add yourdomain.com/*. This is what stops a stranger using the public key they lifted from your page source
03
Both are required. They live in two different consoles, which is exactly why one gets forgotten
⚠️ The failure to recognise: do A but not B and sign-in still fails — with an error that never mentions domains at all, auth/requests-from-referer-…-are-blocked. Meanwhile reading data keeps working, so only login looks broken. That mismatch is the clue.
7
Bonus: Sending WhatsApp Messages ~10 min
01
Reading the database at 7am is only half of it — something has to deliver the reminder. We use one small shared service, notify-hub, that owns the WhatsApp channel, and every app borrows it rather than each wiring up its own
💡 This is not just tidiness. Meta allows exactly one webhook URL per app, so if replies are ever going to come back, something has to own that single URL and route messages on to whichever app they belong to.
02
NOTIFY_SHARED_SECRET — set on both sides to the same value. The app proves it is allowed to send; the hub proves a reply really came from the hub. Anything else gets a 401
03
NOTIFY_ROUTE_BIRTHDAY — set on the hub only. It tells the hub where to forward a button tap. Miss it and taps are silently dropped as "unknown app"
04
The Meta credentials (WHATSAPP_TOKEN, WHATSAPP_PHONE_NUMBER_ID, WHATSAPP_APP_SECRET) and the phone numbers all live on the hub
💡 Phone numbers sit in one environment variable on the hub and nowhere else — not in the app's code, and not in the database. Apps address people by a name like phil and the hub resolves it. One place to change a number, and a leak of the app's data never exposes anyone's mobile.
🗄️

Connected

The pattern worth remembering: public config identifies, rules authorise, and the service account key is the one thing that must never leave the server. Each of the four settings above fails in its own recognisable way — no rules means "permission denied", no service account means the job says so by name, no authorised domain means sign-in is refused, and no referrer means that odd "requests-from-referer" error.
